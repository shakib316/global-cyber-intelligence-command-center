### Hackers Exploit Critical ASP.NET Anti-CSRF Library Flaw Allowing Unauthenticated RCE
- Source: The Hacker News | Published: 2026-11-23T09:11:56Z | Detail enrichment: enriched
- CVEs: CVE-2026-131914 | Topic signals: active_exploitation
- Summary: Cybersecurity researchers have urged users to discontinue using a legacy ASP.NET anti-CSRF library named Idunno.AntiCsrf ("Idunno.AntiCsrf.dll") following the discovery of a critical vulnerability that has been exploited in the wild. - Technical details: Hackers are exploiting CVE-2026-131914, a critical unpatched Idunno.AntiCsrf flaw enabling unauthenticated RCE in ASP.NET WebForms.

Cybersecurity researchers have urged users to discontinue using a legacy ASP.NET anti-CSRF library named Idunno.AntiCsrf ("Idunno.AntiCsrf.dll") following the discovery of a critical vulnerability that has been exploited in the wild.

The vulnerability, tracked as CVE-2026-131914 , carries a CVSS score of 9.3 out of 10.0. The issue affects versions 0.9.1.0 and 0.9.1 Beta, and relates to an insecure deserialization vulnerability in the Idunno.AntiCsrf.AntiCsrfModule HTTP module.

Idunno.AntiCsrf is a third-party ASP.NET IHttpModule designed to provide double-submit cookie Cross-Site Request Forgery (CSRF) protection for ASP.NET WebForms applications. The open-source project is currently defunct and has not been updated since December 2008.

At its core, the problem stems from the fact that the module deserializes untrusted CSRF form token data using an unkeyed .NET System.Web.UI.ObjectStateFormatter instance without cryptographic MAC or signature verification when handling incoming HTTP POST requests to ASP.NET WebForms (System.Web.UI.Page) endpoints.

This behavior, in turn, can allow a remote attacker to achieve arbitrary remote code execution (RCE). Google's Mandiant division has given the vulnerability a "High" exploitability assessment, adding that exploitation hinges only on a single HTTP POST request with no prior authentication or valid CSRF token.

A now-patched flaw in Ghostscript allows a crafted file to escape the program's security sandbox and run commands on the server that processes it.

Ghostscript is the interpreter that many Linux servers use to convert uploaded PDFs, PostScript files, and images into other formats, often without the application calling it directly.

Security firm pwn.ai showed this week that ordinary upload, preview, and print features in about ten common applications could be tricked into feeding it such a file. The flaw, tracked as CVE-2026-125396 , was fixed on September 8, and there have been no reports of it being used in attacks.

Getting a crafted file to Ghostscript is easy, because an application does not have to call it directly. A common image or document library such as ImageMagick, Pillow, libvips, or a Qt plugin will hand PostScript or EPS content to Ghostscript to render, even when the file is named .png, .jpg, or .pdf. A routine feature like making a thumbnail or cropping a picture can start the interpreter, and the exact path depends on the libraries the application uses.

The underlying bug is a use-after-free in the part of Ghostscript that loads fonts. A crafted document uses it to switch off the checks in -dSAFER, the sandbox that is supposed to stop the document from running commands or reaching files.

The security firm demonstrated the result by feeding such a document through about ten applications and watching a command run on the server, each time as the low-privilege account that does the rendering.

Several of those paths needed no login: an anonymous print job to a shared Debian 13 queue, an emailed attachment that Roundcube webmail processed the moment the recipient opened the message, and public upload forms in the WordPress plugins Forminator and Essential Addons for Elementor.

WordPress Core itself needed more: an account with the ability to upload files, which Authors and higher roles have by default. Although the CVE is classified as a local flaw, the firm's tests reached Ghostscript from the network via print jobs, email, and web uploads. The tested version and the access needed for each application are set out in its impact index .

Artifex , which develops Ghostscript, fixed the flaw in version 10.08.0 on September 8, and is moving the vulnerable internal step into safer code. Ken Sharp, the developer who handled the fix, called that step "an ancient piece of code well known to be a vulnerability, but difficult to eradicate" in the bug report . The CVE was published last week and is scored 8.5 out of 10 in its security advisory .

WordPress had already closed its own upload path in version 7.0.4 on August 12, under a separate identifier, CVE-2026-65640, as noted in its release notes . That fix and the Ghostscript fix cover different points in the same chain, so updating one does not remove the need for the other.

The fix helps only where it reaches the renderer the application actually uses. Updating the host operating system does not update a separate copy of Ghostscript bundled inside a container image or an application, so a document worker can keep running the old code after the host package is replaced.

The bug, tracked as CVE-2026-129975 , affects all software that uses GPGME before version 2.3.0, whether the library is loaded as a shared library, a Windows DLL, or statically linked into the program.

Examples the project gives include most mail clients, many XMPP clients, Samba, and its own Gpg4win, GnuPG Desktop, and GnuPG VS-Desktop packages.

The maintainers have merged a fix in the source code, but there is still no fixed version to install.

The weakness is a path-traversal flaw in the parts of the server that store uploaded images and labels. A file identifier supplied by the caller is appended to the storage folder and written to disk without checking that the result remains within that folder.

### Signal restricts mobile screenshots as it confronts ‘existential threat’ of AI surveillance
- Category: Company & market updates | Deal stage: Not applicable | Publisher: TechCrunch Security | Published: 2026-11-21T21:37:10Z | Detail enrichment: enriched
- Summary: Signal is limiting users' ability to take screenshots in both its Android and iOS apps.
- Business background / implications: Signal is limiting users' ability to take screenshots in both its Android and iOS apps.

Signal announced Friday that it’s limiting users’ ability to take screenshots within the secure messaging app — a response to what President Meredith Whittaker described as the “existential threat” of operating systems that integrate agentic AI.

Whittaker wrote that by giving AI agents the ability to “scan” the information on users’ screens, Windows, Android, and macOS/iOS “are undermining Signal’s ability to independently guarantee privacy.”

“Now, in service of AI agentic capabilities, your sensitive data is being captured, stored, and made accessible to whatever local database or remote server an OS-level AI agent is using at that moment,” she said. “All of this is outside of Signal’s control once the data has been captured, and imperils the privacy of all the participants in a conversation.”

Signal already sought to limit these risks by blocking screenshots of its Windows app by default. Now it’s adding similar restrictions in Android and iOS.

That said, users can disable this setting if they wish, which Whittaker said would “break our privacy guarantees.” She also admitted this is an “incomplete” solution, as it doesn’t “address other more sneaky ways AI agents could potentially access application data.”
